# Self-review, 2026-08-02

Two subagent reviewers were dispatched; both went idle without delivering findings through the
normal channel, so this began as a direct self-review. **The full reviewer report was later
recovered by Kiri from the CLI and is the source of items 7–13 below** — it is far more thorough
than the self-review, and its findings on posted-key misattribution, wake-forged confirmations,
and the unauthenticated socket are the most valuable output of this session.

Where the report and a measurement disagreed, the measurement won, in both directions.

## Fixed

### 0. Two reviewer claims that did not reproduce

The report asserted `"abc".contains("")` is **false** in Swift and that this Mac's
`HIDIdleTime` "never climbs past ~2.6 s". Both were tested directly: `contains("")` returns
**true**, and a control run with nothing posted showed idle climbing normally
(9 → 12 → 15 → 18 → 21 s). Their idle sampling was almost certainly taken while Kiri was using
the machine, which also undermines the control run their disproof (below) depended on.

### 1. The engine's own input made it believe a human was present (critical — re-confirmed)

The reviewer called this disproven, on the grounds that `CGEventSource.counterForEventType`
did not move for posted events. That measurement is real but measures a *different mechanism*:
the HID event counters are not `IOHIDSystem`'s idle timer. Re-tested under control after their
report arrived — idle 39 s, +8 s of nothing → 47 s, one `postToPid` → **627 ms**, then climbing
again 4 s later. Reproducible and unambiguous.

**Measured**: with the machine untouched for 63 s, a single posted keystroke dropped
`HIDIdleTime` to 658 ms. `UserPresence` reads that timer, so the engine would type, observe
"someone is at the keyboard", and report `present` — for as long as it kept working. An agent
running alone overnight would have believed a human was there the entire time, and the
`mayTakeCursor` signal derived from it would have been wrong in the direction that silently
disables the tool.

Worse than a wrong reading: the system was **manufacturing the evidence it used to judge
itself**. Fixed by `InputAttribution`, which records every synthesis and discounts a
last-input moment that coincides with ours.

Two useful details fell out of the measurement: accessibility writes do **not** reset the idle
timer (raw idle stayed at 105 s across an AX write), so only rung 2 and beyond are affected;
and the attribution window is deliberately tight (1.5 s), because over-attributing would hide
a real person, which is the dangerous direction.

### 2. Cursor and focus warnings fired on the user's own activity (high)

The invariance check compared cursor position before and after an action, which cannot
distinguish our movement from the user's hand. A live test flagged "the cursor was moved" for
an accessibility write, which is physically incapable of moving it — Kiri was using the mouse.

A warning that fires on unrelated activity trains people to ignore it, which would destroy the
one guarantee this tool exists to make. Only `hardwareInput` can move the pointer, so movement
under any other rung is the user's. Focus is subtler — an action genuinely can raise its
target — so the test there is whether the app *we were driving* came forward.

### 3. An empty probe confirmed itself (medium — verified against the reviewer's objection)

`readback.contains("")` is always true (measured), so clearing a field reported `confirmed`
regardless of what happened. Empty text is now verified by emptiness. The reviewer believed the
opposite semantics, which would have made the same code fail in the other direction; either way
the explicit empty-string branch is correct.

### 4. A failed attach stranded the virtual display (medium)

`startedByUs` was set *after* `launch()` returned, but `launch()` throws on attach timeout
after the app has already started — leaving a running virtual display that nothing believed it
owned, immune to cleanup. Ownership is now claimed before the wait, with a release on the error
path.

### 5. `virtualScreen` picked the user's external monitor (medium)

"First screen that is not main" selects a real second display when one is attached, which would
park agent windows on a screen the user is looking at — the exact opposite of the intent. Now
matched by name.

### 6. A stuck request would deadlock every future one (medium)

The accept loop is single-threaded and `handle` blocked on an unbounded semaphore. One wedged
request — an unresponsive target can hold an AX call for seconds — would strand the socket
thread permanently and make the app unreachable. Now bounded at 30 s with an error reply.

### 7. Posted text was confirmed even when it landed somewhere else (critical — reviewer)

Rung 2 read its confirmation from `ElementQuery.focused(pid:)`, the app's current first
responder, while labelling the evidence with the element we aimed at. RESULTS.md already
measured this exact case on Safari's address bar: the click fails to focus it, the text lands in
the page, and the reply would read `confirmed` for the wrong field. This broke the tool's
central promise in the one place it matters. Read-back now comes only from the target, and when
text lands elsewhere the attempt names where it went.

### 8. Waking the display forged click confirmations (critical — reviewer)

`focusBefore` was sampled before rung 0. Since every tree is degenerate while the display
sleeps, the focus signature necessarily differs after waking — and rung 2's click verdict is
"focus changed ⇒ confirmed". Every wake-then-click cycle, which is exactly the unattended
overnight case, reported success regardless of outcome. Focus is now sampled after the wake, and
focus-delta evidence is discarded entirely when a wake occurred.

### 9. Nothing prevented the engine from sending a message (critical — reviewer)

The probe hard-refused to post Return; the app passed text straight through, so a newline in a
Discord or Mail composer submits. `type` now refuses control characters unless `submit: true` is
passed explicitly. Related: absent `text` defaulted to `""`, so a request that merely forgot an
argument would silently clear the field — an unrecoverable write. That now errors.

### 10. A substring match could press the wrong button (high — reviewer)

`locate` took `matches.first` from a substring search, so `click --label delete` pressed
whichever element sorted first among several. Ambiguity now errors and lists the candidates.

### 11. `noEffect` was the one verdict never checked against pixels (medium — reviewer)

The fall-through asserted `noEffect` while holding an unused baseline capture — in the case
where the diff is the only evidence available. It now applies the visual check.

### 12. Latent undefined behavior in the pixel diff (medium — reviewer)

`CGContext` was constructed inside `withUnsafeMutableBytes` and drawn into *after* the closure
returned, past the pointer's guaranteed lifetime. Not observed failing at `-O`, but the failure
mode would be silent: an all-zero buffer means every diff reads 0.0 and every visually-verified
action reports "no effect". Both creation and drawing now happen inside the closure.

### 13. One idle connection stalled the entire control plane (critical — reviewer)

`readRequest` blocked in `read()` with no timeout on the single accept thread, so a client that
connects and sends nothing wedges every future request. Now bounded with `SO_RCVTIMEO`.

### 14. The safety indicator never lit (medium — reviewer)

`isDriving` was declared and never assigned, so the menu bar icon was permanently idle —
defeating the architecture's primary user-facing guarantee. It now reflects the router.

## Known and not yet fixed

### A. Engine work runs on the main actor — FIXED

Resolved by `Core/Engine.swift`. Verified at runtime rather than inferred:
`diag` reports `engineOffMainThread: true`.

The shape the constraint forced: `AXUIElement` is **not** `Sendable` (checked against the SDK
directly rather than assumed), so elements cannot cross an isolation boundary at all. `Engine`
is an actor that accepts only `Sendable` inputs — a pid, a `Locator`, a string — and returns
only `Sendable` output, with elements created, used, and discarded inside. `TreeCache` stopped
being an actor in the process: the engine already serializes it, so a second actor added hops
and bought nothing. `CommandRouter` is now a translator with no accessibility code in it.

Original description follows.

### A′. Engine work ran on the main actor (high — historical)

`CommandRouter` is `@MainActor`, and `GhostLadder.perform` is `nonisolated async`. Under
SE-0461 a nonisolated async function runs on the **caller's** executor, so the whole ladder —
including synchronous AX reads with a 2 s messaging timeout each — executes on the main thread.
`CommandRouter.locate()` is worse: it calls `ElementQuery.named()` directly, a full deep walk
that measured 1.2 s on Discord, straight on the main actor.

Consequence: an unresponsive target app can hang the menu bar UI, and a large walk blocks it for
over a second. The cache does not help here — `TreeCache` is an actor, so walks routed through
it correctly run off-main; `locate()` bypasses it.

The fix is not a one-liner: `AXElement` wraps a non-`Sendable` `AXUIElement`, so moving the work
off the main actor requires deciding what crosses the boundary — most likely resolving elements
to a `Sendable` handle inside a dedicated engine actor and never passing raw elements out.

### B. `TreeCache` blocks its actor for the duration of a walk

The walk closure executes inside the actor, so a 1.2 s walk serializes every other cache user.
Acceptable while requests are handled one at a time (see #6), but it stops being acceptable the
moment the accept loop handles clients concurrently.

### C. No rail against destructive actions

The probe deliberately refused to post Return; the app has no such rule. `type` into a
composer plus a stray Return sends a message; `AXSetValue("")` destroys field contents with no
undo. Worth an explicit policy before this is used unattended — Codex's one enterprise knob
being about the locked screen suggests where the real risk is judged to lie.

### D. No element re-fetch after invalidation

Raised by disassembly of Codex's implementation, which ships a `RefetchableSkyshotAXTree` that
re-finds an *equivalent* element after the original handle goes stale — and whose own strings
concede "multiple equivalents; cannot guarantee uniqueness". Our read-back path holds the
original `AXElement` across the action; Electron in particular rebuilds elements on focus, so a
stale handle can read as nil and turn a successful action into a `noEffect` verdict.
`tryPostedEvents` already re-resolves through the focused element, but `tryAccessibility` and
the pixel-diff frame lookup do not.

Their other technique worth stealing: keyboard shortcuts by `AXPress` on the matching **menu
item**, located via `AXMenuItemCmdVirtualKey`. That sidesteps our measured Electron limitation
entirely — Chromium ignores keycode-only posted events, but it honors a menu item press, so
Cmd+A and friends become reachable without any CGEvent at all.

### E. Force-casts in the AX layer — premise inverted

I recorded these as a crash risk. The reviewer showed the opposite: casting to a CoreFoundation
type performs no runtime check at all, so they cannot trap — the compiler even rejects `as?`
there. The real cost is diagnosability: an app returning `kCFNull` for a focused element yields
an `AXElement` reporting role `"?"` with no frame, and the engine says "exposes no press action"
instead of "this app returned garbage". Fix is a `CFGetTypeID` guard before each cast.

### F. Remaining reviewer findings — now closed

All fixed and verified on the signed build: the socket now verifies the peer's **code
signature** (see below); the rung 1 → rung 2 fall-through no longer retypes over a write that
landed; `mayTakeCursor` is false whenever the screen is locked; sub-threshold pixel deltas stay
`unverifiable` instead of claiming `noEffect`, with the threshold raised past a caret blink;
the diff declines when the target rect moved; `ScreenCapture` no longer falls back to display 0;
`ElementQuery` and `label` stop re-reading attributes they already have; `DisplayWake` reuses
its assertion id and `Hold` is finally instantiated; and `TreeCache` evicts dead processes and
refuses to cache an empty fingerprint.

**The socket is authenticated.** Signing the CLI made this possible: connections must satisfy
`anchor apple generic and certificate leaf[subject.OU] = "52K336H235"`, checked against the
peer's **audit token** rather than its pid, since a pid can be recycled between the check and
the work. Verified three ways — the embedded signed CLI is accepted, an unsigned development
build of the same source is refused, and a raw `nc -U` connection is refused.

Consequence worth knowing: `./RocuroniumCLI/.build/debug/rocuronium` no longer works. That is
correct — the supported client is the one inside the bundle — but it means the debug loop is
now build-sign-install rather than `swift build`.

All three items flagged still-open here were closed by later same-day commits: the cache
fingerprint (`489abaf` — richer fingerprint, re-taken on every hit *and* after the walk, plus a
TTL for changes no fingerprint can see), lease refcounting (`1334f89`), and engine work on the
main actor (item A, fixed by `Core/Engine.swift`).

## Found while wiring the display and vision commands (same day, later session)

### 15. A region capture of an occluded window returned someone else's pixels (high)

Found by looking at the output rather than the return code, which is becoming the house method.
The first `screenshot --app TextEdit` implementation captured the *display region* under the
window's AX frame; TextEdit was behind Discord, so the command returned a Discord conversation
at exactly TextEdit's size — a correct-looking image of entirely the wrong thing, and one a
model consuming it would have happily described as "the app". App captures now go through
`SCContentFilter(desktopIndependentWindow:)`, which composites the window's own pixels
regardless of occlusion (and works for windows parked on the virtual display). The reply names
the window and frame actually captured, so ScreenCaptureKit's window pick is auditable.
Region (`--x/--y/--w/--h`) and full-display captures keep the old semantics on purpose: "what
is visible there" is the right question for a pixel diff.
